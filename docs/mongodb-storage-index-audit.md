# MongoDB storage and index audit

All 42 persisted Mongoose schemas and embedded documents were reviewed against model/raw collection queries, filters, sorting, uniqueness, TTL, cleanup, retention and startup at base `c95672f41bbb13cd5a91850e1b6794fc33fd8e0f`.

Secondary indexes: **99 → 92 → 85**; with 42 built-in `_id_` indexes: **141 → 134 → 127** on a fresh database. All unique constraints and TTL durations remain. These are definition counts, not measured disk savings.

The user will recreate the local database. Startup creates declared indexes without removing old definitions. No index-drop code, migration, reset script, production access or existing-data deletion was added or performed.

## Second pass: shared dashboard indexes

At the user's request, query-performance indexes decreased **45 → 38**. Unique constraints (35) and TTL indexes (12) are unchanged. This pass deliberately trades selective dashboard-query efficiency for fewer stored indexes; it is not removal of unused indexes.

| Before                                                                                                                                                  | After                                                                                                    | Tradeoff                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Four machine filter indexes: `worker_machine_status_seen`, `worker_machine_group_status`, `worker_machine_platform_seen`, `worker_machine_release_seen` | One `worker_machine_seen` on lastSeenAt descending, _id ascending                                        | Shared ordered scan for every optional filter and unfiltered pages; may examine more machines for a rare filter.                      |
| Audit time, actor/time, resource/time                                                                                                                   | Retain `admin_audit_time`; remove `admin_audit_actor` and `admin_audit_resource`                         | Actor/resource filtering happens during the chronological scan; rare historical matches can require scanning much more audit history. |
| Abuse account/time, global/time, type/severity/time, severity/time                                                                                      | Retain account/time and global/time; remove `abuse_event_admin_filter` and `abuse_event_severity_filter` | Preserves account-scoped lookup; global type/severity filtering scans more retained event buckets.                                    |

No endpoint, filter, ordering, pagination, authorization, or timeout was changed. Existing 3-second worker and 5-second audit/abuse query limits remain. At larger data volumes, rare or absent matches can reach those limits sooner; fixture success is not a production latency guarantee. Date filters reduce audit/abuse scan ranges when supplied. User-search, processing, scheduling, cleanup, and account-access indexes are unchanged in this pass.

## Stored data and retention

Removed six write-only date fields: account daily usage `dayStart/dayEnd`, account monthly and service monthly usage `periodStart/periodEnd`. Writers stop persisting them. UTC helpers already calculate API period/reset boundaries from request time or period key. Counters, keys, revisions and purgeAt remain unchanged.

Retain immutable admission/recipe snapshots, object identities, replay receipts, security fences, bounded device history, diagnostics and stage timings for retry validation, accounting, cleanup and API history. Embedded schemas already disable generated subdocument IDs; persisted schemas disable version keys. Broad removal of null defaults would change lean response shapes and null-sensitive lifecycle behavior.

Retain all existing expiration policies: abuse detail/summaries, identity fences, usage periods, settled reservations, grants, completed storage cleanup, diagnostics and commands. Pending reservations and unfinished cleanup must not expire. No speculative TTL was added to audit, notifications, client/job errors, history, recovery, enrollment or completion proofs because it could discard replay/security evidence, history or artifact references.

## Why the other indexes remain

- Identity: Firebase UID, owner/installation and active push-token uniqueness; owner cursor paging; recent-device analytics; deletion/recovery scheduling. Singleton policies/fences/observations/tombstones use `_id_` only.
- Administration: UID/email uniqueness, actor/operation replay, shared chronological audit pages with residual actor/resource filters, active-alert uniqueness and state/severity pages. User email/name searches remain indexed pending workload profiling.
- Jobs: created/finished overview/export ranges, status/owner history, request uniqueness, admission capacity, upload/terminal/deleted-object cleanup, claim eligibility and unique execution ownership. Finished-time indexes serve overview aggregations.
- Notifications: job/outcome and delivery target uniqueness; due dispatch/delivery; owner/active registration scans; prefix-based deletion. Completion records preserve replay/history.
- Usage: account/month and account/day uniqueness also serve deletion; logical-attempt uniqueness prevents duplicate grant numbering; existing TTLs preserve settlement/replay windows.
- Abuse: bucket/monthly uniqueness; account/global chronological pages with residual type/severity filters; expiry; unique account restriction lookup.
- Releases/storage: channel/build and object-key uniqueness; release/chronological access; orphan/due/owner-pending cleanup; completed cleanup TTL.
- Workers: credential/enrollment uniqueness; one shared chronological machine index with residual status/group/platform/release filters; slot/attempt uniqueness; claim/job-attempt replay; attempt lease recovery/history; pending commands; diagnostic sequences/history and expiry.

## Validation boundaries

The shared-dashboard integration test compares every cursor page against an independent natural-scan reference across 300 synthetic records per collection, including tied timestamps and optional filters, and checks unhinted indexed plans without blocking sorts. The fresh-database integration test initializes every persisted schema, verifies actual unique/TTL/partial definitions, checks indexed owner/job/machine access, rejects duplicate identities and checks machine attempt history without a blocking sort. Usage integration checks concurrency, replay, UTC daily/monthly rollover and absence of removed fields in raw stored records.
