## Findings

### P1 — Bind interpreter links and the complete executable runtime inventory

`worker/musicmute_worker/profiles.py:327`–333 validates only the recorded regular
files. Inventory creation at lines 613–619 explicitly excludes symlinks, including
the actual `venv/bin/python` used by `SeparatorEngine` and transient execution.
Admission neither checks that executable's resolved identity nor detects added
files. A retargeted interpreter link passes admission while executing a different
runtime; added `.pth`, `sitecustomize.py`, or importable modules can likewise change
execution without changing the fingerprint. This is an integrity/completeness bug,
not a claim that a privileged contributor can be made trustworthy by local hashes.

Bounded reproduction executed in a temporary directory, without changing the real
prepared environment: construct a qualified test `PreparedRuntime` with the valid
cached Kim model, matching report, two correctly hashed regular runtime files and
`venv/bin/python` symlink. After baseline admission succeeds, retarget that link to
`/usr/bin/false`; admission still succeeds. Add an unexpected runtime Python file;
admission still succeeds. Output was `RETARGETED_INTERPRETER_ACCEPTED` and
`ADDED_RUNTIME_FILE_ACCEPTED`. A separate read-only observation confirmed the real
prepared `/private/tmp/musicmute-w02-prepared-final/venv/bin/python` is a symlink to
`python3.12`. No substituted interpreter was executed.

Expected fix: include and verify permitted link targets/resolution or materialize
the executable safely; constrain all links to the prepared runtime. Compare the
current executable/importable inventory against the approved inventory, with an
explicit safe policy for generated bytecode and other mutable files. Bind the
actual interpreter, not only its neighboring original binary. Add tests for link
retargeting, unexpected runtime files, unchanged runtime success and safe generated
files. Do not weaken the Python archive extraction policy to achieve this.

### P1 — Use verified native media tools throughout the worker path

`worker/musicmute_worker/worker.py:196` and `:231` still execute bare `ffprobe` and
`ffmpeg` through PATH in `inspect_audio`. The managed runtime is passed only to the
separator. Both source preparation (`:645`) and final output validation (`:749`)
use this unbound helper. On a fresh contributor machine with only the successfully
prepared runtime, a claimed job fails at probing; with system tools installed, the
job runs a different decoder than the hash-bound qualification/checkpoint identity.
Changing that system decoder does not invalidate the runtime fingerprint.

Source inspection establishes the calls directly. Read-only inspection of the
cached, locked FFmpeg wrapper archive found its selected member
`imageio_ffmpeg/binaries/ffmpeg-macos-aarch64-v7.1` and **no ffprobe member**. Thus
simply changing ffprobe to a neighboring path is insufficient.

Expected fix: thread verified explicit media-tool paths through every worker probe,
decode/preparation and validation call. Either add a complete hash-bound ffprobe
asset, or implement an equivalent verified FFmpeg probe contract that preserves
the existing stream-count/type/codec/rate/channel validation. Include these tools
in preparation, inventory, fingerprint and admission. Add a focused end-to-end
worker media-path test with no system ffmpeg/ffprobe available, plus the relevant
malformed/unsupported-media checks. The Mac qualification report must distinguish
its separator-only pipeline from this worker orchestration until that passes.
