## Enrollment and security

The trusted `FleetController` requires an active Google session, matching owner, recent Firebase auth time and the backend worker-registration permission before requesting the existing invitation route. These local checks are preliminary; the existing backend verifies the bearer identity and administrator authorization again. Account owner/generation is checked before storing the invitation. After this durable handoff, the separate fleet enrollment can recover while the app account is signed out.

A current-user DPAPI record in `fleet/enrollment` stores installation/machine credentials and stable exchange, qualification-upload, confirmation, report and activation request IDs before their use. It validates SID, API origin, Windows 22H2+ x64 consumer profile, physical DXGI identity, report/model/inventory bindings and bounded schema sizes. It never writes worker credentials to app account exports or process environment. Store errors prevent advancing or claiming work; explicit recovery reloads the actual journal before replaying. An expired invitation remains an explicit blocker, without silently creating a replacement identity.

`WindowsFleetPreparation` distinguishes personal readiness from enrollment qualification. It checks the installed signed consumer archive identity, requests `windows-user` artifacts with the restricted installation credential, verifies signed update metadata, pins the model and downloads only the backend-approved fixture into its protected digest-derived path. Root's owned Prepare runner executes that fixture under its native mutex and validates its exact hash. The resulting current-SID/GPU/runtime/model/recipe evidence is uploaded with the existing bounded qualification grant protocol before report/activation. The personal fixture is never substituted for backend approval. Approved qualification evidence is stored at a fixed private path and revalidated before fleet runtime startup.

The signed archive digest is distinct from the combined preparation/folder identity. The consumer artifact client refuses an omitted, changed or service profile when the caller requested `windows-user`; omission preserves legacy callers.

## Runtime composition

`createFleetSessionPort(context)` implements the session supervisor's eligibility/reconcile/intent/graceful-stop/sleep port and exposes authenticated role commands for the admission broker. It atomically publishes only non-secret fixed child paths; runtime credentials stay in DPAPI. A protected, expiring control ticket binds the actual owned Node role nonce/birth and the actual server helper identity. The parent verifies native Job Object membership before connecting, and the one-use pipe nonce is rotated for every connection.

The fixed child entry validates its argv through the native agent's Windows-only bootstrap. `createFleetWorkerRuntime` verifies consumer release inventory/ACLs, the approved qualification receipt, model pin and actual physical GPU/driver/ordinal. Fixed dynamic imports load the verified packaged ESM `WorkerRuntime`, `MachineSupervisor`, isolated transfers and hint client, preserving their guardian/transfer module-relative paths. It uses the existing session/config/register/claim/lease/transfer/completion runtime, one qualified DirectML slot and the Windows engine guardian. No service/HKLM adapter or fake production runtime is used.

The child requires the native agent's concrete `PersonalAdmission` client and a physical GPU guard before preloading. There is no success or CPU fallback when admission is unavailable. The conservative inference tracker marks possible work before start/restart and reports idle only after the real shared supervisor completes full teardown. `admission_pending`, `inference_proof`, `guard_acquire` and `guard_release` use the authenticated private role channel; stale GPU/guard capabilities, abandoned locks and failed teardown keep admission closed.

## Transition table

| Action                   | Saved session intent           | Accepted work                                               | Physical behavior                                                                                                    |
| ------------------------ | ------------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Start / Resume           | running                        | Existing ownership and backend authority stay authoritative | Session reconciles the enrolled/prepared role; the shared runtime still checks backend permission and GPU admission. |
| Pause                    | paused                         | Finishes accepted attempts                                  | Prevents new claims; does not become Stop.                                                                           |
| Drain                    | draining                       | Finishes accepted/uncertain claims                          | Exposes progress; completion requires the same runtime's lifecycle acknowledgement.                                  |
| Stop                     | stopped                        | Requires acknowledged drain and zero accepted attempts      | Pending drain returns `FLEET_DRAIN_PENDING`; ordinary controls preserve the role until safe teardown.                |
| Restart                  | Preserves current saved intent | Requires the same safe drain                                | Does not turn an explicit Stop into Start.                                                                           |
| Sleep                    | Saved intent unchanged         | Existing lease/runtime reconciliation handles resume        | Temporarily pauses new admission; resume reconciles saved intent.                                                    |
| App close / app sign-out | Unchanged                      | Continues in the session agent                              | Closes UI/account work only.                                                                                         |
| Windows logout           | Retained for next login        | Session teardown policy applies                             | Native supervisor may terminate only the exact owned trees.                                                          |
| Confirmed revoke         | stopped first                  | Backend unpair uses `force:false`                           | Revokes the credential-owned machine only after safe control; no implicit purge or service removal.                  |

`SessionState` is the only saved intent authority. The enrollment record has no competing intent; it retains an onboarding revision solely to prevent delayed automatic Start from overriding a session command during setup. A lost command response remains visible and explicit restore reads the confirmed session state back.
