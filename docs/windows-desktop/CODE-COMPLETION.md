# Windows code-completion and acceptance map

Reviewed 2026-10-10 in the shared development checkout. This is the W33
feature-by-feature source deliverable: **all 30 COVERAGE points and all 93
FEATURE-ACCEPTANCE journey items** are mapped below. Each journey retains the
accepted requirement, actual receiving action/resource, visible state, meaningful
fixture/fault proof and an existing named W34 case. A source file or test count
alone is not treated as feature closure.

**All33 implementation and available-code-check tasks are closed.** Final W03,
W12, W22, W26 and W31 source returns, W30 security review and the frozen whole
regression are reconciled. This closes source work while preserving every deferred
Windows, real-service and release gate. Actual Windows compilation, DirectML inference, installation, dialogs,
Chrome, live accounts/R2/fleet, listening/performance and release remain unrun.

Accepted support stays **Windows 10 22H2/build 19045 native x64 and Windows 11
x64**, no x86/ARM/emulated Windows; model inference needs a qualified physical
DirectML GPU. There is one shared Chrome extension. The consumer worker is
no-admin, per-user and runs only in the logged-in Windows session. Guest local
processing, account saving and administrator-authorized fleet participation retain
separate authority. Store, Windows ARM, Linux and optional tray refinements are
later ideas, not substitutes for the accepted website/desktop requirements.

## Inventory and production authority

The requirement inventory is [COVERAGE](COVERAGE.md) and
[FEATURE-ACCEPTANCE](FEATURE-ACCEPTANCE.md). The initial
[SOURCE-MAP](SOURCE-MAP.md) is a porting baseline; its old planned/partial wording
is not used as proof of current behavior. The current
[parity inventory](../../windows-desktop/docs/parity-inventory.md), detailed
requirement ledgers cited per point and [security review](SECURITY-REVIEW.md)
provide the reviewed receiving/resource/denial boundaries.

All desktop UI actions below enter actual
[renderer App](../../windows-desktop/src/renderer/app.tsx) →
[typed preload](../../windows-desktop/src/preload/index.ts) →
[closed command parser](../../windows-desktop/src/shared/contracts.ts) →
[Main](../../windows-desktop/src/main/main.ts) sender/window/intake gates before
the named receiving modules. Main composes Host/current-user native storage,
actual factories, session/media/storage ports and subscriptions. Synthetic
services in portable fixtures do not establish an installed Electron/Win32 run.
The production [built IPC fixture](../../windows-desktop/tests/desktop-ipc-transport.test.tsx)
executes restricted built preload, production ingress and real React DOM; its
native/account services are deliberately injected. Account tokens, transfer grants, private native paths, process identities and GPU
ordinals are not renderer-provided authority. The DROP_INPUT source path is
derived by trusted preload from a user-dropped File; Main still enforces sender,
Windows path and one-use selected-file capability checks.

Chrome has its separate actual
[browser service](../../windows-desktop/src/main/browser/service.ts) →
[verified account authority](../../windows-desktop/src/main/browser/account-authority.ts)
→ provider/private media route. It cannot forward desktop/fleet commands or
choose an account generation. Session/worker Native operations remain fixed
roles with protected peer/birth/nonce, not a privileged service fallback.

Journey IDs `Pxx.Jyy` enumerate the existing line items in their original order.
They are report locators, not a replacement acceptance contract. Source fixture
filenames and faults link actual behavior; dated ledgers retain exact historical
commands. Final whole-regression state is separate from those historical proofs.
