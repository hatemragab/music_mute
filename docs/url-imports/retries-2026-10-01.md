# URL import retries — 2026-10-01

New URL imports have one initial acquisition attempt and at most three automatic
retries. Only transient dependency, upstream-refusal and scratch-disk failures
before upload/job reservation are eligible. The persisted delays are 5, 10 and
20 seconds; queue capacity and provider start-rate limits may extend that wait.
Permanent validation, source-unavailable, account, access and policy failures end
the import immediately. Historical failed imports are not bulk replayed.

The backend owns retry scheduling. The same import/request identity, canonical
URL, trim setting, frozen recipe, shared producer/generation and acquisition
duration hold survive the backoff. The public status returns to `queued` until
the next execution. Clients continue their existing owner-scoped WebSocket
subscription; no polling, timer, or new create request is required. A terminal
manual retry uses a new request ID and the original URL/trim choice.

Each execution claims the next persisted attempt with a compare-and-set fence
and receives a fresh opaque UUID for one adapter call. Attempt-specific BullMQ
IDs prevent a completed earlier execution from swallowing its successor. MongoDB
is the durable scheduling outbox, so normal server maintenance recreates missing
delayed queue entries after Redis errors or restart. A stale execution cannot
claim an early retry, cancel a newer execution, or release its hold.
The persisted 15-minute execution deadline includes dependency reads and
reservation work as well as transfer. Slow preparation cannot extend the old
download beyond the recovery window and overlap its successor.

Shared waiters remain queued through eligible retries. Only a permanent failure
or exhausted fourth attempt fails the shared producer and releases the one
acquisition hold. Successful submission exchanges it for measured processing
duration exactly once. Existing accepted jobs and recorded storage intents are
checked first; uncertain PUTs are recovered with bounded object verification,
without another acquisition. A recorded input key or job reservation forbids a
fresh acquisition even when the transfer response was lost.

The processing-job retry policy is described separately in
[processing retries](../processing-retries-2026-10-01.md). This URL import change
requires deployment of the updated backend; a provider/router deployment alone
does not activate it. The provider can charge for each permitted acquisition
attempt. Retries cannot guarantee that an unavailable source or refused Google
transfer will eventually succeed.

## Validation coverage

Focused unit tests cover the bounded retry policy, frozen reservation reuse,
execution/queue fencing, restart outbox repair, account policy checks, recorded
upload protection and accepted-job recovery. The loopback MongoDB/Redis shared
media integration fixture additionally exercises delayed success, four-attempt
exhaustion, single holds, retained shared waiters, permanent failures, account
disablement and uncertain successful PUT recovery. These fixtures make no paid
provider calls and do not establish production behavior.

## API review

The [official Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/)
were read on 2026-10-01. Rules 104 (endpoint security), 106 (backward
compatibility), 229/231 (idempotent requests), 253 (asynchronous processing) and
177 (safe error details) shaped the change. Existing authenticated routes and
response shapes are preserved; ownership, request identity and execution
generation fences remain server-owned. No additional polling or transport is
introduced. These checks do not establish production compliance.
