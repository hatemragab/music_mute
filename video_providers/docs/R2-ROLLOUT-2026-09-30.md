## Resource and security read-back

Before deployment, both adapters still had the previous 128 MiB scratch and
256 MiB memory ceilings. Those cannot accommodate main's twenty concurrent
100 MB scratch reservations. Only their `serviceUpdateOverride` was updated to
the checked-in configuration: **2 GiB `/work` tmpfs, 3 GiB memory ceiling**, one
CPU, read-only root, initialization enabled, all capabilities dropped, and bounded
5 MiB/two-file logs. These limits are ceilings rather than reservations. No
resource purchase was made. The router's existing source-matching 128 MiB memory
and half-CPU override was preserved.

Independent app-definition comparisons confirmed for all three apps:

- One configured replica; private web exposure setting enabled.
- No published ports, custom domains, or persistent media volumes.
- Every environment key/value and each pre-deploy hook unchanged.
- Service overrides match current main source exactly.
- Shared acquisition concurrency/rate settings have no explicit legacy override;
  current source defaults are twenty active requests and five starts per second.
- Vendor credentials stay only in their adapters; hooks continue injecting
  protected internal service keys. No storage/database/Firebase credentials were added.

The CapRover `/user/system/info` endpoint exposed only SSL/domain configuration,
not host RAM. Host memory capacity could not be measured through that endpoint.
No established SSH access was available; no credentials or server addresses were
guessed. Docker container health state, actual running-image/source hashes and
worst-case twenty-file memory behavior were not independently measured. This
record establishes CLI deployment, configuration preservation and startup,
not full live acquisition or load qualification.
